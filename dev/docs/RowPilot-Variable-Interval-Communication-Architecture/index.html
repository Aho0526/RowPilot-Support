Executive Summary

This document defines the communication protocol and transaction model for programming Variable Interval workouts on Concept2 PM5 monitors. Unlike standard fixed-distance or fixed-time workouts, Variable Intervals require a stateful, multi-frame transaction to overcome payload limitations and firmware buffer constraints.

Technical Context

The Problem: Single-Frame Failure

Initial implementations attempted to pack all intervals (Work/Rest pairs) into a single CSAFE frame.

  • Confirmed: Up to 4 intervals typically succeed.
  • Confirmed: 5 or more intervals consistently fail.
  • Observation: The PM5 accepts the packet (checksum passes), and the UI may show a brief loading state, but the workout is never committed. No standard error codes (e.g., 384-1) are returned.
Silent Failure Mode: The PM5 does not return standard error codes when the single-frame approach overflows its internal buffer. This makes debugging difficult without deep state monitoring.

Payload Size Limit Hypothesis

Hypothesis: The PM5 firmware has a restricted input buffer (~64–128 bytes) for reassembled CSAFE commands when combined with SET_WORKOUT_TYPE. Overflow causes a silent rejection with no standard error code returned.

Multi-Frame Append Strategy

The State Machine Hypothesis

The PM5 firmware is hypothesized to operate a "Workout Builder" state machine that remains active as long as the device stays in a configuration phase.

[*] ──────────────────────► Idle
         SET_WORKOUTTYPE(0x08)
Idle ──────────────────────► BuilderActive
         SET_INTERVAL_INDEX(n) + DATA + CONFIGURE(0x14)
BuilderActive ─────────────► BuilderActive  (repeats per interval)
         SET_DISPLAY_WORKOUT(0x13)
BuilderActive ─────────────► WorkoutReady
WorkoutReady ──────────────► [*]

Why CONFIGURE (0x14) in Every Frame?

Hypothesis: The 0x14 command acts as a "Commit Interval" trigger. Without it, the data for a specific index may stay in a volatile buffer. It also prevents the PM5 from timing out the builder session by proving an active configuration sequence is in progress.

Packet Structure Examples

Initialization Frame (First Interval)

Sets the workout type and the first interval's work/rest parameters, then triggers CONFIGURE_WORKOUT.

Frame 1: SET_WORKOUTTYPE(0x08) | SET_INTERVAL_INDEX(0) | [work/rest data] | CONFIGURE_WORKOUT(0x14)

Subsequent Intervals

Each additional interval is sent as a separate frame, incrementing the interval index.

Frame 2: SET_INTERVAL_INDEX(1) | [work/rest data] | CONFIGURE_WORKOUT(0x14)
Frame 3: SET_INTERVAL_INDEX(2) | [work/rest data] | CONFIGURE_WORKOUT(0x14)
...
Frame N: SET_INTERVAL_INDEX(N-1) | [work/rest data] | CONFIGURE_WORKOUT(0x14)

Finalization Frame

After all intervals are sent, SET_DISPLAY_WORKOUT commits the entire transaction to the PM5 UI.

Final Frame: SET_DISPLAY_WORKOUT(0x13)
Inter-frame Delay: A 150ms delay is inserted between configuration frames to comply with the CSAFE specification and ensure the PM5 firmware has time to process each interval before the next frame arrives.
